# Threat model v1 (REQ-131 — reviewed at every WP exit; changes logged at the bottom)

## Assets, in order

1. Ledger integrity (append-only history + hash chain + external timestamps) — the product IS this.
2. Tenant isolation (per-tenant D1; the REQ-025 suite is the proof).
3. Evidence bytes (photos/signatures in R2) + their hashes.
4. Device signing keys (driver phones) and JWT secrets.
5. Money projections (invoices, GL export).
6. Tenant identity separation (REQ-167 — no tenant/person/customer/vendor names in this repo).

## Adversaries & surfaces (STRIDE per surface)

| Surface | Top threats | Standing mitigations |
|---|---|---|
| API (`/v1`, `/mcp` later) | tenant-id tampering, token forgery, replayed mutations | claim-only tenant resolution (client tenant ids hard-rejected), JWT verify + schema-parse, tenant-scoped Idempotency-Key, Zod at every boundary (REQ-133), unauthenticated paths reveal nothing (401 before routing) |
| Ledger | event mutation, back-dating, silent correction, chain fork, seq races | no UPDATE/DELETE paths + BEFORE INSERT guards (I3, CI-linted in migrations), server-assigned hash chain, daily Merkle→TSA (WP-02), DO-per-stream seq mutex — see the WP-02 review below |
| Driver PWA | stolen device, GPS spoofing, offline tampering | device keypair non-extractable (WP-05), geofence + accuracy radius disclosed (REQ-018), lockout (REQ-069), location consent as event (REQ-166) |
| Email in/out (WP-06/07) | spoofed inbound, exfil via evidence email | DKIM/SPF/DMARC, sender verification before event attribution, suppression list (REQ-092/157) |
| CI/supply chain — dependencies | poisoned dep, leaked secret, identity leak | lockfile-pinned installs, gitleaks, OIDC (no static deploy tokens), REQ-167 denylist lint |
| CI/supply chain — **gate inputs** (assets, not deps) | **T**ampering (a crafted asset moves pixels inside a baseline the gate treats as the specification), **D**oS (a stranger's deploy fails our gate with no change of ours), **I**nformation disclosure (a third party learns what our screens render, and when CI runs) | a canonical capture may depend on NO origin we do not control: the visual project aborts the public demo basemap (vector tiles AND glyph PBFs) before navigation, then asserts that the set of foreign origins whose requests actually COMPLETED is empty — `tests/visual/screens.spec.ts:264-293`. | Deploy configuration | **T**ampering (a "make the scopes symmetrical" edit fills in a fail-closed omission), **E**levation-of-privilege (a test affordance or the test JWT canary reaching prod), **D**oS (a worker ships dereferencing an unbound binding; an unprovisioned resource reads as provisioned) | every deployable scope must declare the dev binding surface, as a MERGE gate (`tools/deploy/wrangler-scope-parity.test.ts:29-43`); the required-secret contract mirrors `docs/ops/DEPLOYMENT.md` and BLOCKs on absence (`tools/deploy/preflight.ts:63-114`, `:250-265`); one logical binding must resolve to one physical resource (`preflight.ts:224-248`); the load-bearing omissions and the prod test-affordance ban are test-locked (`tools/deploy/preflight.test.ts:467-487`). ## WP-02 review — ledger tampering & timestamping (new)

| Threat | Vector | Mitigation / status |
|---|---|---|
| Chain fork | A client supplies its own `seq`/`prev_hash`/`hash` to branch history | The sequencer parses request bodies as `EventInput` (which carries NO `seq`/`prev_hash`/`hash`/`stream_id`) and assigns them server-side; `LedgerEvent.parse` is a `.strict()` backstop. `hash` is computed, never client-supplied. CLOSED. |
| Seq race | Two concurrent appends read the same tail and assign the same `seq` | DO-per-stream serialization mutex. LOAD-BEARING because a Cloudflare DO input gate closes only during the DO's OWN `ctx.storage` ops (and `blockConcurrencyWhile`) — it does NOT span a plain D1 subrequest await, and this sequencer reads its tail + writes its batch via D1. Deleting the mutex turns the 100-concurrent test red with `SQLITE_CONSTRAINT` on the duplicate `(stream_id, seq)`. CLOSED. |
| Silent REPLACE | `INSERT OR REPLACE` under D1's `PRAGMA recursive_triggers=0` skips the BEFORE DELETE guard and rewrites a row | BEFORE INSERT guards on events/positions/money_lines fire while the old row still exists (migration 0003); the load path uses plain INSERTs only. Regression-tested in schema-core.test.ts. CLOSED. |
| TSA receipt validation | A forged/replayed RFC 3161 timestamp response | Structural DER parse + genTime/imprint/nonce checks (`assertGrantedReceipt`) PLUS, as of WP-16, cryptographic verification (`verifyTsaSignature`, `packages/ledger/src/tsa/cms.ts`, REQ-014): the CMS SignerInfo signature over the DER of `signedAttrs` is verified via Web Crypto (RSASSA-PKCS1-v1_5 or ECDSA-P256, both SHA-256), the `messageDigest` attr is confirmed = SHA-256(TSTInfo) and `contentType` = id-ct-TSTInfo, and the signer cert is chained (issuer/signature) to a CONFIGURED trust anchor, time-valid at genTime, carrying the id-kp-timeStamping EKU. Fail-CLOSED on every failure (invalid sig, digest mismatch, no chain, expired, missing EKU, unsupported alg). It is an OPT-IN seam: with no `trustAnchors` supplied it returns an explicit `chain-not-configured` state (never a silent pass), and the protocol verify stands. CLOSED. Remaining as DEPLOYMENT concerns (NOT offline-verification gaps): (a) revocation (OCSP/CRL) — needs network, checked at stamping time, out of scope for archival replay; (b) the real TSA's trust-anchor certs are config supplied at deploy (out-of-repo F1 [CONFIRM]; `HttpTsaClient` is fake-tested only; the in-repo verifier is tested against a SELF-GENERATED synthetic test CA). |
| Anchor day-bucket skew | An airplane-mode upload back-dates `ts` to mutate an already-anchored day | Merkle day-bucketing keys on `recorded_at` (server clock at append), never actor `ts`. CLOSED. |
| Lens / geo leakage | A counterparty/driver lens reveals events, positions, or precise geo outside its scope | Server-side lens filtering + per-event visibility + redaction; the adversarial cross-lens suite (workers/api/test/lens-adversarial.test.ts) has INDEPENDENT guards on the geo/city sweep (case 9b), so a scoping regression makes it fail rather than pass silently. CLOSED. |

## T14/T15 review — CI gate inputs, deploy configuration, evidence integrity (new)

The V1 close-out changed the security surface in three areas — CI gate inputs, deploy configuration, and the integrity of a release record. Of the six rows below, two are CLOSED outright; two are closed only within a stated scope (the capture; the declared shape), with the wider question still a hold; two are recorded OPEN — one as a class this repo cannot close on its own, one because the check that would catch it cannot currently fire.

| Threat | Vector | Mitigation / status |
|---|---|---|
| A third party can fail (or move) a CI gate | The blessed-screenshot diff fetched a live public demo basemap — vector tiles AND glyph PBFs — serving a moving `latest` build. Measured at ~3.6% of the 1440×900 frame against the 2% `maxDiffPixelRatio`: a stranger's cartography deploy could fail this gate with no change of ours, and a crafted tile could move pixels inside a baseline the gate treats as the specification. | The visual project aborts that host before any navigation, then asserts the ACTUAL dependency rather than the intent: a `requestfinished` listener records the origin of every request that COMPLETED, and the test fails unless that set is empty of everything but our own dev servers and the RFC-2606 `.example` api host (which cannot resolve, so a finished request to it is proof it was fulfilled by a pinned payload). A rename, a self-host swap (REQ-075) or a newly-introduced third-party asset therefore goes RED instead of quietly re-opening the capture — `tests/visual/screens.spec.ts:264-293`. The assertion is hard (the screenshot diff beside it is the soft one). Under `--mode merge\|release` the harness turns that failure into exit 1, and an absent browser into BLOCKED, never a green (`tools/harness/playwright-guard.ts:59-105`); locally it stays advisory (REQ-158). **CLOSED FOR THE CAPTURE ONLY.** The production tile source is untouched and remains a documented hold (REQ-075). |
| A blessed baseline of a fail-closed state | Three of five canonical screens were capturing error surfaces (a re-auth prompt, a uniform status-unavailable deny), and the command screen was capturing five network-failure panels because its ready selector waited for a `canvas` that the failure state also renders. A blessed error state is a bug promoted to a specification — and it makes the gate blind to the one regression it should catch loudest: a real surface silently degrading into a denial. | Every screen now asserts a POSITIVE marker of its authed surface AND the absence of its failure text — the board's live status line, the party hero, the resolved public milestone, the driver day sheet (`tests/visual/screens.spec.ts:180-242`). CLOSED. |
| An unasserted secret requirement reads as satisfied | The preflight's required-binding contract declared NO secrets for billing or agents while `docs/ops/DEPLOYMENT.md` requires three. Their absence returned a clean bill of health for a billing worker that cannot verify a Stripe webhook signature (so it would accept forged callbacks) and an agents worker that cannot send a single evidence email. | The contract now names `STRIPE_WEBHOOK_SECRET`, `PLATFORM_INTERNAL_SECRET` and `RESEND_API_KEY`, and an absent one is a BLOCK, never a WARN (`tools/deploy/preflight.ts:73-95`, enforced `:250-265`). Pinned both ways — the contract's content and the resulting BLOCKs — in `tools/deploy/preflight.test.ts:296-319`. CLOSED. |
| **A plausible value reads as provisioned** (the reusable one) | The placeholder check is SHAPE-based. Billing's staging platform-database id was a well-formed random UUID: it passed, so an unprovisioned database read as provisioned — while the api's all-zero id on the SAME logical binding was correctly flagged. Two workers were addressing two different physical databases and the gate said nothing. | Partial, and stated as partial. The ids converged and BOTH now block (`tools/deploy/preflight.test.ts:499-531`); a second, shape-INDEPENDENT check requires one logical binding to resolve to one physical resource across every worker (`preflight.ts:224-248`); and every committed placeholder is now deliberately unmistakable — all-zero UUIDs for D1, and KV ids that are *not* 32-hex precisely because a valid-shaped hex id would read as provisioned. **OPEN as a class:** no in-repo check can distinguish a provisioned id from a plausible one. Only an account-side fact can — `preflight --state`, without which every account-side fact is UNPROVEN and therefore blocked (`preflight.ts:489-546`). **The general rule: a shape check answers "is this well-formed", never "does this exist". Where the two are confused, the well-formed lie wins.** |
| A fail-closed omission filled in by a tidy-up | All five workers now declare a complete `[env.prod]`. The next edit that makes the scopes "symmetrical" would bind the agents' evidence sender (turning a NotConfiguredSender into a live sending path) or the translator's EDI transport (CONFIRM-gated, REQ-154) — an absence is exactly what a helpful symmetry edit fills in. | The absences are asserted as absences, and test-only send affordances are banned from prod (`tools/deploy/preflight.test.ts:467-487`); scope shape is a merge gate, so a config edit fails in the PR rather than in staging (`tools/deploy/wrangler-scope-parity.test.ts:29-43`). Declaring a shape is not provisioning it, and the gate still says so: `preflight --env prod` reports 26 BLOCKs, `--env staging` 12. CLOSED for the shape; provisioning stays an account-side hold. |
| A release record proves the wrong tree | A promotion record binds to a commit, environment, fixtures hash and deployment, and `evaluateEvidence` refuses any record whose four fields disagree with the promotion context (`tools/release/evidence.ts:98-124`, proven `tools/release/evidence.test.ts:120-142`). But its only caller builds that context FROM the record it just wrote (`tools/release/run-gate.ts:142-144`), so the comparison is self-satisfied by construction and can never fire; no separate consumer of `evaluateEvidence` exists in this repository. A record therefore proves its gates ran — nothing machine-checks that it is the record for the tree being promoted. | ~~**OPEN**~~ **CLOSED 2026-08-02** (was: recorded in `docs/ops/RELEASE-EVIDENCE.md` §"It does not prove"). **SUPERSEDED 2026-08-02 (audit §16, commit `10a95f5`) — NO LONGER SELF-SATISFIED.** `run-gate.ts` now RE-OBSERVES the promotion context after the gates run (`gitHead()`, `fixturesHash()`, and the two env vars read afresh) instead of copying it from the record it just wrote, so all four comparisons are live. That also makes them useful BEFORE any promote step exists: a gate run spans minutes, so a commit landing or a fixtures-manifest change mid-run now invalidates the record instead of being certified by it. Pinned by a source-reading test in `tools/release/run-gate.test.ts` (main() is not exported and shells out to git) and mutation-proved — restoring the copied form fails 3 of its 4 assertions. Exposure is latent, not live: no promote step exists yet, so there is nothing today that could consume the wrong record. The fix is that the promote step, when written, derives its context independently — the git SHA it is about to promote, the environment it is promoting into, the deployment it observes — and never rebuilds it from the record. |

# WP-13 — MCP v1 (book from Claude) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task (fresh subagent per task, spec-review then code-quality-review between tasks). Written for an engineer with zero SHUDDL context.

**Goal:** An MCP server that lets an external Claude quote / book / track / document / approve freight on tenant-#0, where **every mutating tool runs the identical server-side gate as a human/CSR** (no bypass) and **spend caps + gates are enforced in the worker, never by the model** — proven under hostile-prompt tests.

**Architecture:** A **new standalone Cloudflare Worker `workers/mcp`** (mirrors the WP-12 `workers/translator` additive pattern) that speaks MCP (JSON-RPC `tools/list`/`tools/call`) + an OAuth 2.1 authorization server. It reaches the existing gated verbs through a **Cloudflare service binding** to the api worker (`env.API.fetch(...)` runs the api worker's Hono app in-process through **every middleware and gate unchanged** — the api worker exports `default app` at `workers/api/src/index.ts:187`). Each tool is a thin JSON-RPC→REST adapter. A paired company authenticates via OAuth → a `pairings` row (`kind='mcp'`, already a legal CHECK value) → the worker mints a short-lived internal `SessionClaims` JWT (which `workers/api/src/middleware/auth.ts` already accepts) with tenant taken **only** from `pairing.tenant_id`. Spend caps are a single fail-closed chokepoint in the mcp worker.

**Tech Stack:** TypeScript strict (no `any`), Zod at boundaries, Cloudflare Workers + service bindings + Durable Objects (OAuth/MCP session) + KV (grants), Cloudflare Agents SDK `McpAgent` + `workers-oauth-provider`, Vitest (`@cloudflare/vitest-pool-workers`), pnpm workspaces.

## Non-negotiable invariants (verified in the understand sweep)
1. **No-bypass:** the only write path to `booking.created` is the DO `#enforceBooking` (`workers/api/src/do/sequencer.ts:648-692`); no route emits it directly. The mcp worker appends **at most `quote.accepted`** (via the accept-quote route) and lets the unchanged Booking agent produce the gated booking — the WP-12 translator precedent.
2. **Tenant + company isolation (REQ-025):** tenant from `pairing.tenant_id` ONLY (never a client header/body — mirrors `auth.ts:12-13`); every read flows through the party **lens** (`packages/ledger/src/lens.ts`), never a raw SELECT in the mcp worker, so redaction (REQ-192) is inherited.
3. **Caps/gates are server-side, prompt-independent:** enforced in worker code keyed off the OAuth-derived `pairing_id`, never a model-supplied field. The external client holds an OAuth token to the mcp worker only — it never holds an api JWT (the worker mints the internal JWT and never exposes it), so it cannot call `/v1/*` directly to bypass the chokepoint.
4. **Budgets:** no new event kind (35 frozen), **no new D1 table** (22-ceiling; the spare is spent by WP-12 `integrations`). Caps limits live in `pairings.caps`; the running tally is a zero-table read (a VIEW/query over `money_lines`/the quote sell, attributed via an additive `shipments.refs.pairing` stamp). DOs are not tables.

**Context:** An MCP client completes OAuth 2.1 (remote-MCP standard) → the grant binds to a `pairings` row (`kind='mcp'`, `db/control/migrations/0001_control.sql:19`; carries `tenant_id`/`scopes`/`caps`/`secret_ref`/`status`). `principal.ts` resolves the pairing (status='active') and mints a short-lived HS256 `SessionClaims` JWT with `JWT_SECRET`: `{ sub: "mcp:"+pairing_id, tenant: pairing.tenant_id, role: "ops", pairing_id, exp }` — **role bounded to `ops`, never finance/admin** (so the principal structurally cannot emit `credit.checked` or satisfy a finance-required approval), **tenant only from the pairing**. **Key tests (RED-first):** a valid grant mints a JWT `auth.ts` accepts (tenant==pairing tenant, role==ops, pairing_id set); an inactive/unknown pairing → 401; a client-supplied tenant/role is ignored; `SessionClaims.parse` still accepts a legacy token with no `pairing_id`.

## Task 8: Server-side spend caps (REQ-105) — the net-new gate

**Files:** Create `workers/mcp/src/caps.ts`; wire it into `gate.ts` `beforeMutation`; Test `workers/mcp/test/caps.test.ts`.

**Context — THE highest-risk item (no existing implementation to reuse).** Limits live in `pairings.caps` (`{spend, velocity, lanes}`, exists). The **running tally is a zero-table read** attributed via `refs.pairing`: `spend` = the sum of the accepted-quote sell of the pairing's shipments booked in the rolling period (read via `callApi` over the money/quote projection or a `money_lines` view joined on `refs.pairing` — pick the honest source that reflects committed spend at book time); `velocity` = count of bookings in the period; `lanes` = allowed origin/dest set. `beforeMutation` computes `tally + this_booking` and **fail-closes (a 4xx, EDI-style; or routes to the existing HELD/`approval.requested` path) when it would exceed a cap** — using existing semantics, **no new event kind, no caps table**. The check is keyed off `session.pairing_id` (from the OAuth token), **never** a request field, so a hostile prompt cannot alter it.

**Key tests (RED-first, prompt-independent):** a booking that would exceed `caps.spend` is refused fail-closed (the shipment does not book); bookings up to the cap succeed and the tally advances; a `velocity` cap blocks the N+1 booking in the period; an off-lane booking is refused; the cap keys off the token pairing_id and **ignores** any `pairing_id`/`cap` field the caller puts in the tool args (a hostile-prompt case).

**Commit:** `feat(mcp): server-side spend/velocity/lane caps at the mutation chokepoint, fail-closed (REQ-105)`

## Task 9: Confirm-before-money gate (REQ-108)

**Files:** Create `workers/mcp/src/confirm.ts`; wire into `beforeMutation`; Test `workers/mcp/test/confirm.test.ts`.

**Context:** A money-moving mutation (`book_shipment`, `approve` of a money-moving approval) requires a structured explicit confirmation in the tool args (e.g. `confirm: { intent, amount_cents }` matching the quoted amount). **A no-confirm or mismatched-confirm mutation FAILS** (server-side, in `beforeMutation`) — the model cannot self-authorize money movement. Read-only tools (quote/track/document) need no confirm.

**Key tests:** `book_shipment` without a `confirm` block → refused; with a `confirm.amount_cents` ≠ the quoted sell → refused; with a matching confirm → proceeds (then caps still apply).

**Commit:** `feat(mcp): structured confirm-before-money gate (REQ-108)`

|---|---|
| Caps in the tool wrapper (per-tool, forgettable) | Single `beforeMutation` chokepoint every mutating tool funnels through (Task 3/8) |

| Idempotency drift on duplicate tool calls | Deterministic key from the JSON-RPC id (Task 3) |
| iCloud dup / env fragility | Sweep dups + full `pnpm verify` at exit (Task 12) |

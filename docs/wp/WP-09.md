## The load-bearing decisions
1. **Both no-auth surfaces live on `/pub/*`, never `/v1/*`** — so the blanket auth + idempotency middleware can never run on a session-less path (idempotency reads `session.tenant` and would throw). The public path constructs no `SessionClaims` and never calls `lensFor`, so the `lensFor` else-branch (`{scope:tenant}=1=1`, which legitimately serves admin/ops) is unreachable from anon. `lensFor` is NOT modified.
2. **The status page is a signed CAPABILITY token, not a slug or a per-shipment JWT.** The tenant+shipment live INSIDE a domain-separated MAC (`STATUS_SECRET` ≠ `JWT_SECRET`), so neither is client-forgeable or enumerable, a session JWT can never verify as a cap (and vice versa), and there is no stored column to drift from a `status_cache` rebuild. The read is PROJECTION-ONLY with a positive-allowlist body, so no event kind widens to `public` and the frozen 35-pair visibility snapshot is byte-untouched.
3. **Public geo is ALWAYS city-coarse — even post-OFD.** The party lens unlocks exact geo at out-for-delivery; the public cap URL is FORWARDABLE, so it must NOT. `generalizePosition(pos,false)` unconditionally, re-parsed through a `.strict()` sub-schema so `accuracy_m` can't leak.
4. **The guest quote is a PREVIEW, not a ledger write.** A stranger's speculative quote leaves ZERO residue (Law 2 — anon traffic can't write unprunable rows); the price comes from the pure engine, the response is the counterparty-redacted allowlist, and the tenant is the routing-authoritative hostname (not a forgeable `Host`).
5. **Every counterparty read is fail-closed by construction.** Doc-row visibility is DERIVED from the recording event (never a lens bypass); margin internals are stripped at ANY depth (structural walk); a new `status_cache`/payload field is not emitted (positive allowlist) — so a future field defaults to hidden, not leaked.
6. **booking.created is idempotent per stream (exit-audit).** The DO gate rejects a second booking on a stream that already has one, so the new portal accept-quote seam can't force a duplicate booking or regress the read-model.

## WP-exit audit swarm (REQ-119)
A 6-lens adversarial swarm ran at exit (attack → independent refutation → synthesis), weighted to the FIRST public no-auth surface — no-auth enumeration/tenant-confusion, margin/PII/geo leak, lens-scoping/cross-party, the C-1 positions fix completeness, booking-gate + append-only integrity, and tenant-isolation/abuse. Every finding had to survive an independent verifier. Both survivors were fixed with proving tests and re-verified. **No open Criticals at close.**

**Found + CLOSED:**
- **CRITICAL C-2 — the new portal write seam could force a DUPLICATE booking.** WP-08's `#enforceBooking` never enforced its "first event on a fresh stream" assumption; WP-09's `accept-quote` seam made it reachable — a portal party re-rates + re-accepts an already-booked shipment, the fresh `quote.accepted`'s new deterministic id evades the Booking agent's id-dedupe, and a second `booking.created` appends (append-only pollution + a delivered shipment's `status_cache` regressing to `booked`). → The DO gate now rejects a `booking.created` on a stream that already has one (VALIDATION_FAILED `shipment_already_booked`, unbypassable across the WP-10 command-bar path + races), and the Booking agent skips cleanly (GUARD 3). The Concierge quote-stage path stays green (its shipments row has no `booking.created`). REQ-191. Proving tests both ways (DO gate + agent skip + no regression).
- **IMPORTANT I-1 — `division` leaked to the counterparty on `booking.created`.** A REQ-179 redaction-law gap on the first counterparty read seam. → Strip `booking.created.division` + (forward guard) `dispatch.assigned.driver_user_id` for the non-tenant lens; a GENERAL fail-closed test asserts no known-internal key survives the party lens for ANY counterparty-default kind.

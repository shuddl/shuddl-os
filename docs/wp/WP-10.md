## The load-bearing decisions
1. **The command bar is a DETERMINISTIC palette, not an LLM.** The DoD is "20 canonical commands" — a fixed verb set. No LLM/NL parse in the command app keeps REQ-024 clean and the surface auditable; any future NL parse is an agents-port.
2. **The CSR intake is discrete gated write seams, reused by MCP.** `POST /v1/parties` + `POST /v1/shipments` are plain ops-gated REST endpoints (WP-13 MCP calls the same ones); the booking still flows through `#enforceBooking` — the intake never bypasses a gate, and the quote-stage shipments row carries no `booking.created` so the WP-09 one-booking-per-stream gate stays green.
3. **KPI honesty is absolute.** Every tile is a real drillable number or the literal `UNKNOWN`. OR has no true operating-cost source, so it is honestly relabeled "Cost/Rev (quoted basis)" rather than fabricating a true OR; DSO gets a minimal AR-settlement projection so its number is real; a no-data tile shows "—", never a lie.
4. **Queues read the DURABLE ledger, not clobbered projections.** The exceptions queue reads the append-only `exception.raised`/`osd.captured` events (a later `pod.signed` clobbers `status_cache.state='exception'`); the approvals queue is a real projection with a server-side `required_role` decision seam.
5. **The copilot is read-only and grounded.** A pure core over a lens-scoped injected read port, cite-or-abstain (whole-answer abstain on any ungrounded citation), the LLM confined to `packages/agents` and never called in CI — it can never write, fabricate, or answer across the caller's visibility boundary.

## WP-exit audit swarm (REQ-119)
A 6-lens adversarial swarm ran at exit (attack → independent refutation → synthesis), weighted to the new write surface (CSR intake), KPI honesty/leak, the approval authorization, the copilot's read-only/cite-or-abstain, tenant isolation across every new read, and append-only/read-model consistency. 12 raw findings; 2 survived independent verification, both MINOR. **NO OPEN CRITICALS — WP-10 is clear to close.**

**Found + CLOSED (both MINOR, both fixed this pass):**
- **5.1 (REQ-197) — the exceptions queue could silently drop an open exception at scale.** `readEvents` orders by `stream_id, seq` and caps at 1000, so the exceptions route truncated lexicographically BEFORE its JS `ts`-sort; past 1000 lifetime exception events, an open exception could vanish (contradicting the module's "never lost" claim — the ledger stayed intact, so a read-view completeness bug, not integrity). → The durable read now orders `ts DESC` (index-backed) + paginates by a `before_ts` keyset, so the page retains the freshest and older is reachable. (The fix also closed a latent D1 bound-parameter 500 in the shipment-state `IN`-join.) Proving tests: a fresh open exception surfaces past the cap; the cursor pages older; the default `seq` path unchanged.
- **0.1 (REQ-196) — intake and the Concierge did not converge on party identity.** The Concierge's `findPartyByEmail` was case-sensitive and the id domains differed, so a CSR-created `Bob@Acme.com` + a later Concierge inbound `bob@acme.com` created a DUPLICATE party (a split-billing risk downstream; confined to the mutable `parties` table — no gate/integrity break). → Both paths now derive the email-keyed id via one shared `partyIdForEmail` (`@shuddl/contracts`) and find case-insensitively, so they resolve to ONE row. Proving tests: a contracts parity test + a cross-worker convergence test (CSR party found, not duplicated, by the real Concierge consumer).

**Strong negatives (attacked hard, HELD — close-out evidence for the new surfaces):** the approval `required_role` authorization held under TWO independent attacks (a forged `approval.requested` self-decide + injecting `required_role` via the generic route) — the server-side matrix does not trust a client role; tenant isolation is CLEAN on every new WP-10 read route (`events?kind`, approvals, exceptions, kpis, board); the KPIs are truthful (no fabricated tile, no margin-basis/interline-floor leak, no cross-lens read); the copilot held (no write, no fabrication, no lens-escape — a live-LLM answer citing a real-but-non-supporting event was refuted by `groundOrAbstain`); the AR-settlement read-model held under THREE attacks (a `Math.abs` refund flipping paid, two mis-settling-the-wrong-invoice probes); and the party find-or-create + booking gate held (no name-keyed mis-book, no Idempotency-Key order-drop). 6 of 6 Critical categories probed, none broke.

## Assumption log
- **Device-attested GPS:** the device SIGNS its own geo stamp, so a stamp is attributable to a device key — this is attribution, NOT a server-truth cross-check of the coordinate. A server-side plausibility check (speed/teleport, tower/Wi-Fi corroboration) is a future hardening, not a WP-05 claim.
- **Evidence photos are hash-bound, byte-verify deferred:** hash-at-capture binds the payload to the bytes the device saw; verifying the recorded hash against the UPLOADED R2 object is **REQ-168** (WP-06). Until then the gate binds the POD to a placed-photo EVENT+HASH, not to stored bytes (see the exit audit residual, below).
- **`operating_state` is the canonical uppercase USPS code** ("TX", never "tx"/"Texas"); capture, the reverse-geocode derivation, and the consent gate must all agree (exact, case-sensitive compare).
- **Client flow is a strict MIRROR of the server gate** (shared `REQUIRED_EVIDENCE` tokens → a drift is a compile error); the server always re-checks. The client never authorizes a transition.

## WP-exit audit swarm (REQ-119)
Four adversarial auditors ran at exit (gate reachability/bypass, driver forgeability, offline merge integrity, honesty/DoD), each attempting to BREAK a defect class and RUNNING the code to confirm. Every Critical was fixed and **independently re-verified closed. No open Criticals at close.**

**4 Criticals — found + CLOSED:**
- **Delivery fabricated-photo-hash** — `assertDelivery` cleared its placed-photo pillar on any 64-hex string. → Now the POD's `placed_photo_hash` must EQUAL the `photo_hash` of a prior `freight.photographed{placed}` EVENT on the stream (mirrors the pickup gate's real-event requirement). Re-verified: a bare hash with no matching prior placed photo → `["placed_freight_photo"]`.
- **Driver-forgeable override** — an override author was taken from the client. → The DO binds `{by}` to the elevated-role session subject (`session.sub`); a non-elevated caller cannot self-authorize.
- **`device_id` not bound to the signing key** — a device could claim any `device_id`. → The `device_id` is derived from / verified against the device public key at append; a mismatched claim is rejected.
- **Forced-photo stub** — an early capture path could satisfy the photo gate without a live frame. → `frameDataUrl` returns null with no real video (never fabricates); ADVANCE stays disabled (`CameraScreen.test.tsx`).

**3 Highs — found + CLOSED:**
- **Consent "XX"** — an UNKNOWN jurisdiction was consentable. → `assertConsentBeforeGps` hard-blocks the `XX` sentinel regardless of any consent; `ConsentAck` can no longer carry `XX` (belt + suspenders).
- **Interline sender-not-receiver** — the sender's own `actor.device` signature was mistaken for the receiver's ack. → `assertInterline` requires a non-empty `payload.cosig` (the RECEIVER's co-sign), distinct from the transferring party's signature.
- **Client merge global-not-per-stream** — merge dedup keyed globally could drop a legitimate cross-stream event. → merge keys on `(device_id, device_seq)` per stream; airplane soak re-verifies zero loss / zero dupes.

**Residuals (recorded, not open Criticals):**
- **Placed-photo byte-verification** — the gate binds hash→EVENT, not hash→BYTES; a caller able to emit events can still land a POD over a never-uploaded photo. Recorded as **REQ-168** (WP-06 byte-verify at upload), annotated at the gap.
- **Minor:** an override-elevated-role set / finance dead-branch (unreachable given the gate order) — noted, non-blocking, no behavior change.

**Strong negatives (attacked hard, held):** gate enforced identically on every API path (no UI-only gate); a delivery outside the fence with no override is blocked; the forced photo is untypassable; offline merge never overwrites; consent gates the first GPS stamp; device signatures verified at append; the client flow cannot authorize a transition the server would block.

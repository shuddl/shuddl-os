## The five load-bearing decisions
1. **Double-book is made impossible by a D1 partial-UNIQUE index on a slot claim, NOT by a gate alone.** Two bookings for one slot are two DOs whose appends do not serialize, so a "read occupancy then block" gate has a TOCTOU race. SQLite serializes writes: the second concurrent claim's `db.batch` hits `ux_legs_slot` and the whole append aborts. The capacity gate is UX for the sequential case; the index is what makes the DoD literally true. **`appt_service_date` is IN the key** — a date-less unique would bind a recurring slot forever (the design panel caught this).
2. **The slot claim lives on `legs` (ALTER ADD columns), not a new `appointments` table.** The 22-table budget has one spare; appointments are naturally leg-scoped, so nullable `ALTER ADD` + a partial unique index is budget-clean and semantically right. `legs` is a mutable domain table, so `appointment.set` may UPDATE it (unlike the append-only `events`).
3. **Capacity N = N discrete capacity-1 slots.** `capacity_slots` enumerates bookable `door×window` units; an appointment claims exactly one. "Not double-booked" = "the slot key is UNIQUE" — no atomic counting.
4. **The booking gate targets the `bill_to`, not the consignee (REQ-182 corrects GA-6/REQ-047).** The `bill_to` is the party the Biller's `resolveRecipient` emails; gating its contact is what makes demo #1's evidence email guaranteed-deliverable. Gating the consignee (the literal GA-6 wording) would have let a broker booking pass and then the email silently hold. `booking.created` is also the party-correction point that closes the WP-07 self-reference.
5. **Every acceptance path funnels through ONE gated `booking.created`.** `quote.accepted` → the queue-triggered Booking agent (deterministic ids, DO dedupe, idempotent redelivery, gate-block-holds); the manual/MCP path (WP-10) and the inbound-accept path (WP-07 deferred) append the same gated event — so the credit + recipient gates enforce on every path (REQ-030).

## Assumption log
- **One leg per (shipment, kind) in v1.** `booking.created` materializes one `pickup` + one `delivery` skeleton leg; the appointment projection UPDATEs by `(shipment_id, kind)`. Multi-stop / multi-leg-per-kind is a later refinement — recorded, not built.
- **Facility config is operational data, not transactional.** `facilities.hours`/`capacity_slots` are seeded/administered config (like `rate_config`), read server-side by the gate; there is no `facility.*` event kind. Changing a facility's hours is an ops action, not a ledger event.
- **`credit.checked` is a recorded FINANCE decision, not a bureau call.** WP-08 authorizes who may record it (finance/admin, REQ-185) and enforces the recorded state (REQ-042); it does not compute creditworthiness. The `credit_status` projection is last-write-wins pending the REQ-183 ordering hardening.
- **The honest transit window is zone×zone business days, display-only.** Absent or malformed → the line is OMITTED, never fabricated; it never blocks or delays a price. Dims/lane refinements are WP-09.
- **`shipment_id` is the stream's, always.** After REQ-186 the DO derives `shipment_id` from `stream_id` (`s:<id>`); an event can no longer carry a shipment_id other than its stream's. Non-shipment streams (`q:`/`t:root`) carry none.

## WP-exit audit swarm (REQ-119)
A 6-lens adversarial swarm ran at exit (attack → independent refutation → synthesis) — **double-book / atomicity**, **gate bypass / server-side parity**, **tenant isolation**, **money / party-correction / credit**, **idempotency / redelivery**, and **append-only / read-model / honest-window**. Each lens attacked the WHOLE integrated WP (cross-task seams the per-task reviews couldn't see); every finding had to survive an independent verifier before it counted. Both surviving findings were fixed with proving tests and adversarially re-audited. **No open Criticals at close.**

**Found + CLOSED:**
- **CRITICAL — `credit.checked` was client-appendable by any driver/ops (gate bypass → mis-bill).** The kind was not server-emitted, not gated, and the driver write-scope only checks the *shipment*, never `payload.party_id` — so any driver could POST `credit.checked{party_id:B, status:'clear'}` and overwrite an arbitrary party's tenant-global `credit_status`, defeating the REQ-042 credit-hold gate (a held party ships on credit; ops clearing a hold is a segregation break). No single task owned this: T1 typed the kind, T4 projected it, T6 gated *booking* on it — none authorized *who may emit it*. → `credit.checked` is now a PRIVILEGED finance decision enforced at the write boundary before the DO append (only finance/admin; finance reaches the route only for a privileged decision), REQ-185. 6 proving tests + an adversarial re-audit confirming no residual/new bypass (the DO is the sole write boundary; agents never emit it; variant strings that dodge the guard are rejected by the DO's `EventInput.parse` before appending).
- **MINOR + defense-in-depth — an omitted/crossed `shipment_id` committed a phantom / 500'd.** The client `shipment_id` is `z.string().optional()` and was trusted; an omitted one committed an `appointment.set` that claimed no slot (projections key off `e.shipment_id`), a crossed one reached a projection as an unmapped 500 (contained only by the `events` CHECK). → The DO now DERIVES `shipment_id` from the stream (`s:<id>`), closing both for every kind, byte-safe (the SEED-1 hash is unchanged), REQ-186. 2 proving tests + a re-audit confirming no flow regression.

**Registered (recorded as scope, not left as silent gaps):** REQ-185, REQ-186 (fixed this WP); REQ-183 (credit-projection write-ordering, WP-11) and REQ-184 (ratecon generation, vNEXT) carried from the per-task reviews.

**Open-but-tracked (NOT a residual of this WP's fixes):** REQ-183 — the credit-hold gate is defeat-proof by *authorization* now (REQ-185); it is defeat-proof by *write-ordering* only once REQ-183 ships in WP-11. Called out by the Fix-A re-audit as the remaining half of the same end-to-end property.

**Strong negatives (attacked hard, held):** double-book is atomically impossible (`ux_legs_slot` is the sole arbiter, independent of the capacity gate; the DoD is intact under simultaneous `Promise.allSettled` claims and the DST/tz probes); the three booking/appointment/dispatch gates enforce identically on every API-reachable path (UIs only reflect); NO cross-tenant read of a facility/slot/party/credit_status/document (tenant pinned at the sequencer, each tenant its own D1); the Booking agent + appointment/reschedule are idempotent under at-least-once redelivery (no duplicate/lost booking); NO `UPDATE`/`DELETE` path on `events`, projections stay consistent with the ledger, and the transit window is a real number or omitted — never fabricated.
